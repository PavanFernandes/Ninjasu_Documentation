# Fix spec: group payment and cancel review findings (2b.9, 2b.10)

Five defects found by blind Codex reviews of commit 4f7ef92. Repo: `ninja delivery service java`. You cannot run Maven or a database: read the code carefully. Do NOT edit the checkout files (`service/schedule/checkout/*`, `ScheduleCheckoutController`, `OrderGroupRepository`); another job is changing them. Add or adjust unit tests (JUnit 5 plus Mockito, no database) for every fix. Keep files under 250 lines where they are already under it, and comments to one sentence stating the rule.

## A. Late capture on a FAILED or CANCELLED group cannot be refunded when the amount differs (payment, high)
`GroupPaymentSettlement` records an orphan capture on a FAILED or CANCELLED group and asks `GroupRefundService.raise` for a full refund, but `GroupRefundServiceImpl` builds the normal slices (every member grand total plus fees plus round-off = payable_total) and uses the actual captured amount only for CAPTURE_MISMATCH. If a 100 rupee checkout was cancelled and 90 rupees were captured later, the slices total 100, `GroupRefundMath` throws, and the whole settlement transaction rolls back (the payment id is not recorded and no refund is requested; the sweep only looks at CREATED groups). Fix: for a group in FAILED, CANCELLED or CAPTURE_MISMATCH the refund is the ACTUAL captured amount, built by the same code path CAPTURE_MISMATCH uses today (read it and `GroupRefundAmountMismatchTest`); a PAID group is unchanged. Add tests: CANCELLED group, 100 payable, 90 captured: one refund request of exactly 90 and no exception; FAILED group with the exact amount; PAID group unchanged.

## B. Verify says success for a payment that is not captured (payment, medium)
`GroupPaymentServiceImpl.verify` returns the group view without settling when Razorpay reports the payment as authorized or otherwise not captured, and `SchedulePaymentController` answers SUCCESS with the message "Payment verified." although the group is still CREATED. Fix: the controller message depends on the returned `paymentStatus` (PAID: a verified message; anything else: a message saying the payment was received and is waiting for capture), and add a controller or service test for both. Do not change the response shape.

## C. Late cancel can refund a delivered order (cancel, high; the flag is off by default)
`ScheduleCancelServiceImpl.lateCancelMember` checks only the order status and queries only non-terminal deliveries. Rider completion commits the delivery as DELIVERED before the projection updates the order, so in that gap late cancel sees the old order status, ignores the DELIVERED delivery and raises a refund. Fix: refuse (BusinessRuleViolationException, writes nothing) when ANY delivery of the order, including terminal ones, has status DELIVERED; add the repository query you need to `DeliveryRepository` (read it) and a test for the gap (order status OUT_FOR_DELIVERY, delivery DELIVERED).

## D. Legacy active-order query can return a Schedule member (cancel, medium)
`OrderServiceImpl.getActiveOrder` (around line 146) calls a repository query with no `groupId IS NULL` filter and an excluded-status list that omits live states, so a released Schedule member in PLACED or ACCEPTED can come back as the Eat Now active order. Fix: add `groupId IS NULL` to that query (or add a new query for it), update the classification lists in `OrderRepositoryGroupFilterTest` so it passes and pins the rule, and add a test that a group member is not returned while an ungrouped order still is.

## E. Seller status guard may read a stale order (cancel, medium)
`OrderServiceImpl.updateOrderStatus` loads the order with `findByIdAndShopIdAndOrderType` and later takes `findByIdForUpdate`; with the same persistence context the managed entity can keep its stale status, so a seller DELIVERED write could overwrite a concurrently committed CANCELLED. Fix: after the locking read, refresh the managed entity from the database (inject the EntityManager the way other services do, for example `RefundState`, and call refresh) before checking CANCELLED or DECLINED and before the transition validator; ungrouped Eat Now behaviour stays otherwise identical. Test with a mock EntityManager that the refresh happens after the lock and that a status flipped by the refresh is refused.

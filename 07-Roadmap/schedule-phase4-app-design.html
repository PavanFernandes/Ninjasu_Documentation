Schedule lunch in the customer app

Every screen and state the Phase 4 slices (4.1 to 4.4) add to Food-Ninja-Frontend, drawn with the app's own tokens: the pink hero band, Inter headings over DM Sans body, white 16px cards, the dark CartBar pill and the outlined ADD button. Decisions this design takes

What is fixed before the screens

D3 · switch placement (recommended option)

Eat Now / Schedule toggle in the Home hero

A two-segment toggle sits directly under the location row, inside the pink band. It appears only when the context says area.scheduleEnabled. Schedule mode keeps the Home tab and the bottom bar, swaps the cuisine dial for the slot strip, and the location row reads "Lunch · Today".

D3 · intro screen (recommended option)

HSR intro shown once

The first tap on Schedule opens a full-screen intro that explains how it works: choose a delivery time, order before the time shown, get one delivery for the whole order. Seen-flag lives in usePreferencesStore. "Not now" also marks it seen and returns to Eat Now. A "How it works" link above the delivery times opens the same screen again at any time.

Signature element

Delivery time first, ordering deadline second

Each ticket shows the approximate delivery time, an explicit "Order by" time and a text countdown that turns amber near closing. The selected ticket has a tick as well as a pink border. There is no progress bar, because the server sends no window or stock level to draw one from. Availability always comes from the server.

Rules carried from the plan
  • The app never decides availability or price. Greying uses the server's slot.orderable and dish reason.
  • The countdown is display only; at lastCallAtMs (skew-corrected by serverNowMs) the app re-reads context.
  • Errors branch on data.error, never the HTTP status.
  • Every cart call sends type=FOOD&fulfilment=SCHEDULE; the Eat Now cart is never touched.
  • The app never says how many or which restaurants can go in one order. The server decides; the app only shows its refusal (F11).
  • Customer text avoids internal words: "delivery time", not "slot"; "ordering closed", not "last call".
Kept as is
  • Brand tokens, fonts, hero band, tab bar, ADD button, CartBar shape.
  • The existing customize sheet, login prompt and ConfirmDialog patterns.
  • The existing Schedule group screen (My Orders); 4.4 adds to it rather than replacing it.
Out of scope here
  • Advance days above 0 (day picker): today is same-day only.
  • Group push notifications (2d.2) and picked-up / delivered stages (3.3).
  • COD for Schedule, and the web app.

Slice 4.1 · feature/schedule-4.1-area-bootstrap

Area bootstrap: the toggle, the intro, and the four "can't order" states

useScheduleContext(lat, lng) reads GET /api/schedule/context from the saved location. Guests can browse; the login gate comes at ADD.

Slice 4.2 · feature/schedule-4.2-slot-menu

Slot-first menu, add, and the three cart refusals

The slot comes first, then restaurants and dishes. ADD goes through the guest gate, the customize sheet (when customizable), then POST /api/cart/items with schedule {areaId, serviceDate, slotId}.

One mapping table: reason → chip copy (F7) and refusal copy (F12). The menu feed sends only ORDERABLE, SOLD_OUT and ORDER_BY_PASSED (any other reason hides the dish), so only those two ever show as a chip; the other rows appear only in the add refusal (F12).

For the reviewer (Codex, ChatGPT, or a person)

Review questions

Each one is a choice this page made that could reasonably go the other way. Answer by frame number.

  1. Toggle placement (F1). Inside the pink hero, under the location row. The other options: a chip in the white filter row, or a separate tab. Does the hero placement read as a mode switch rather than a filter?
  2. Hero copy in Schedule mode (F1, F7). The location row changes from "Delivery in 15 mins" to "Lunch · Today". Is it clear enough that the customer is now in a different flow?
  3. Delivery time tickets (F1, F7, F13). Each shows "Delivery around 12:30 PM", an "Order by" time and a text countdown ("8 min left", amber near closing). Is the countdown helpful, or does it pressure people? Should it show only in the last hour?
  4. Unavailable dishes (F7, F8). Greyed dishes stay in place with a reason chip, and a restaurant with nothing orderable collapses to one row at the bottom. Should sold-out dishes move to the bottom of their restaurant too?
  5. What the time means (all tickets). "Order by 11:30 AM" is when ordering stops; food arrives around 12:30 PM. The server sends only a start time per delivery time, so the app can't show a range like "12:30 to 12:45". Is "around" enough, or should the server send a window end?
  6. Delivery time closed in the cart (F18). "Browse times" keeps the cart; adding an item for a new time asks to clear it (F10). A seamless "move my cart" would need a backend change. Is the extra step acceptable?
  7. Payment states (F20, F20b). One state per screen, each ending with "don't pay again". Are "Confirming" (after verify) and "Checking" (after the sheet is closed) different enough to keep apart? (OD5)
  8. Which restaurants can be combined (F11). Only a count is built. Pairing by distance, by dish, or with Ninjasu's own kitchen would be a server rule; the dialog text already works for any such rule. Is a generic "can't be delivered together" message enough, or should the server send a reason?
  9. Unfinished payment (F17, F17b). Is "Cancel order" safe to show next to "Pay", given the server checks the gateway before cancelling? F17b offers only "View order".
  10. Cancel confirmation (F22). No amount is shown before cancelling. Is "full refund to your original payment method" enough reassurance?
  11. Missing states. Is any state from plan §3 or the backend error list missing here? Known gaps: offline or timeout on the context read (uses the shared ErrorState), and the guest login prompt at ADD (uses the existing LoginPromptModal, so not drawn).
Example values: prices, fees, GST and restaurant names are invented, and the arithmetic in F13 and F15 adds up only so the mock is consistent (GST 5%, fees split equally between restaurants in the F15 member totals). In the app, every amount is a server field.

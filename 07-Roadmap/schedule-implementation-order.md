# Schedule — Final implementation order

**Final review (2026-10-15):** Claude (devil's advocate, Raphael, marketer lenses) and Codex reviewed this plan. Changes folded in: the order/group schema and idempotency keys (2b.4), a resequenced 2b (reservation and refund cores before the payment core), a group refund core with a lease and gateway-receipt dedupe (2b.7), capture-amount validation (2b.9), legacy-endpoint guards, the prepaid `codAmount` fix moved before rider assignment (2d.7), a backend price-preview endpoint instead of web-side pricing (2b.3, 5.1), a CA gate before pricing (0.7), a fulfilment-policy design (plan decision 43), and the ticket-fire rule (plan decision 42). Task ids 2b.4-2b.11 were renumbered.

**Pricing re-plan (decided 2026-10-18, Samivan):** there is no split price. Each add-on option gets a dine-in price and an online price (2b.12); commission is a flat-rupee slab per item unit from the restaurant's named commission plan, computed on the order and never shown in a menu price (2b.13). The split-price model, `MenuPriceResolver` and the price-preview endpoint (2b.3, 5.1) are superseded; paid add-ons are allowed on Schedule dishes; 2b.2 is re-planned as three PRs.

## 2. Code facts this plan is built on (verified 2026-10-15)

- `SHOP_BOARD_ACTIVE_STATUSES` is derived from all statuses minus terminal/ghost (`OrderServiceImpl.java:55`): a new status leaks onto the live board unless classified explicitly.
- `orders.razorpay_order_id` is UNIQUE (`Order.java:153`); `payment.captured` / `order.paid` resolve it with `findByRazorpayOrderId` (`PaymentServiceImpl.java:447`), while `refund.processed` resolves by `findByRazorpayPaymentId` (`:502`) and only acts on `REFUND_PENDING` orders (`:507`): one payment = one order today.
- `orders.idempotency_key` is NOT NULL and globally UNIQUE (`Order.java:88`): a multi-order checkout needs one derived key per member order.
- Checkout and refund use `order.getGrandTotal()` (`PaymentServiceImpl.java:170, 641`); refunds are whole-order, with receipt `refund-<orderId>` as the gateway dedupe key (`:649`). Confirm (`doConfirmPayment`, `:265-342`) neither validates nor stores the gateway's captured amount. `attemptGatewayRefund(orderId, shopId)` loads a shop and its settlement strategy (`:623-638`); the hourly sweep scans only `Order.paymentStatus = REFUND_PENDING` (`:680`); confirm completes the cart by user + cart type (`:309-310`).
- `getOrderHistory` returns every non-ghost order (`OrderServiceImpl.java:173`). The seller-transition switch has `default -> false` (`:375-383`), so a new enum value compiles; the leak is the derived board list (`:55-58`).
- Confirm decrements the live stock ledger and publishes `OrderPlacedEvent`.
- `cart_sessions.shop_id` is NOT NULL (`CartSession.java:24`); `addToCart` rejects a second shop.
- `OrderAssembler` is single-shop: one radius check (`:108-116`), one `computeDeliveryFee` from shop `DeliveryConfig` (`:304`).
- `assignDelivery` snapshots `codAmount = order.getGrandTotal()` for every order (`DeliveryServiceImpl.java:285`); a delivery has one `shop_id` and one `order_id`.
- Route split transfers the full grand total to the shop (`RouteSplitSettlement.java:39`); no commission exists in code.
- Existing jobs: `PaymentReconciliationJob` (hourly), `ItemStockResetJob` (03:00 IST).
- Shop audit: `AuditAction` enum + `AuditRecorder` (transaction-mandatory); no Schedule actions yet.
- (found 2026-10-18, [02-Domain/menu.md](../02-Domain/menu.md)) A menu item has no price: its price is the sum of the selected add-on options, and one required ITEM group gives the base price. The customer app and the POS both read the same `Addon.price`, so the app shows the dine-in price with no commission today. One price per dish per day cannot express sizes or paid add-ons.

### Phase 2a as built (2026-10-16) — where the code differs from the rows above

The rows above are the plan; this is what shipped. Where they disagree, **this list wins**.

- **Times are epoch-millis `BIGINT`** (`effective_from`, `created_at`, `platform_audit_events.occurred_at`), not `TIMESTAMPTZ`, to match orders and `audit_events`. API fields are `...Ms`.
- **No `scope_type` column** on `commission_rate`: the scope is whichever of `shop_id` / `service_area_id` is set (CHECK: exactly one). Rows are append-only (trigger blocks UPDATE/DELETE/TRUNCATE; entity columns `updatable=false`); a correction is a later row. At most 1 year ahead (`MAX_HORIZON_DAYS`); one row per scope + fulfilment type + moment (partial unique indexes).
- **The percentage `commission_rate` model (2a.4: `rate_percent` per shop/area, `CommissionRateResolver.rateAt`) is superseded 2026-10-18 by named slab plans (2b.13).** It has no production caller yet. The plan assignment keeps its scope, `effective_from`, notice and `consent_ref` ideas; T2a-12/T2a-13 are re-proven against plans in 2b.13.
- **Notice period for a SHOP rate = its area's `commission_notice_days`** (the plan defines only that setting; a shop with no area cannot have a rate). Not yet confirmed by Samivan. For plan assignments this must be re-decided (open in 2b.13).
- **`GET /api/schedule/context` has no `restaurants` yet** (needs the Schedule menu, 2b.2). Returns `area: null` when the point is in no area. `lat`/`lng`/`serviceDate` are strings parsed in the service (a typed parameter would 500 on bad input). Times are epoch-millis.
- **Area DELETE does not exist** (slots can be deleted); an area with shops or rates assigned must never vanish. Area and slot edits take a row lock on the area (`findByIdForUpdate`); no `@Version`.
- **2a.5 audit:** `platform_audit_events` + `PlatformAuditRecorder` (MANDATORY transaction, verified admin only, per-action key allowlists); endpoints declare `@PlatformAuditedEndpoint` (the ratchet test `AuditEndpointDeclarationTest` accepts it). **The shop-level `AuditAction` values for restaurant edits were NOT added**: they belong with 2b.2(b) (moved from 2b.6 on 2026-10-18).
- **2a.6 guard** (`ScheduleSchemaGuard`, `schedule.verify-on-boot`): 21 objects (19 + the slot FK and the area-name index from 2a.7); triggers must be *enabled*, not just present; uses `pg_catalog`; each migration also needs a constraint/index/trigger because Hibernate creates bare tables first. A new Schedule table/column/trigger must be added to its list (a consistency test fails otherwise).
- **Global side effect:** `GlobalExceptionHandler` now returns 400 (not 500) for malformed JSON and a wrong-typed parameter on every endpoint.
- **Verification debt:** T2a-12 and T2a-13 (an order keeps the rate it was priced with) can only be proven in 2b; T2a-14 is proven by mocks plus the ratchet, and the recorder has not yet written a real row (first real admin change). Whole suite: 624 unit tests at 2a.7 (no database); CI only compiles, so run `./mvnw -o test "-Dtest=!NinjaDeliveryServiceApplicationTests"` before merging.

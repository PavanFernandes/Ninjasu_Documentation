Ninjasu Rider App

What the project is, how it works, what's built, and what genuinely isn't — written so the next implementer never has to guess or re-derive an architectural decision alone.

Status as of 9 August 2026

The assign/cancel half of the rider loop is device-verified. A shop's staff manually assigning or cancelling a delivery correctly rings the rider's phone and syncs status — confirmed on a real Android device on 6 August, including the order-decline cascade that used to fail silently. Two real bugs surfaced during that test and were fixed, deployed, and re-verified the same day: a notification-channel registration gap, and a 500 response on order-decline that masked an already-successful state change.

The broadcast/ring/accept loop is not verified. Nobody has watched an order reach READY, watched every eligible rider's phone ring at once, and watched the first tap win. That loop shares almost no code path with what's been tested — treat it as entirely unproven. Closing that gap is what §2's walkthrough and the roadmap's Phase 1 exist for.

01What this project is

Ninjasu is a food-delivery platform built as four codebases sharing one backend and one database.

RepoWhat it isWho uses it
ninja delivery service javaSpring Boot backend + Neon PostgresEveryone — the only source of truth
Food-Ninja-FrontendReact Native — customer + shop-owner in oneCustomers, restaurant staff
Ninjasu_WebNext.js — platform admin + shop dashboardNinjasu admins, shop owners
Ninjasu_Rider_AppReact Native — this projectDelivery riders

The rider app is the newest and least finished of the four. It holds no business rules of its own — the backend owns all logic, and the app simply renders what the API returns.

Two kinds of rider

This distinction drives everything else in the system:

  • Restaurant rider — belongs to one specific shop's own fleet. Only ever delivers for that shop.
  • Platform rider — a Ninjasu-wide rider, reaching shops only by being placed in a delivery zone that contains those shops.

A delivery zone is a named, hand-picked cluster of shops — e.g. "HSR Zone." Admins put shops into a zone and platform riders into the same zone; that membership is what decides whose phone rings.

Two independent shop-side settings

As of ADR-0019 (6 Aug) — this used to be one conflated setting, since corrected:

  • Delivery mode (SELF / PLATFORM / NONE) — who the eligible riders are. SELF = the shop's own fleet only. PLATFORM = own fleet plus riders in a zone covering the shop.
  • Dispatch mode (MANUAL / BROADCAST) — how dispatch reaches them. MANUAL = staff pick a rider by hand, works under either delivery mode. BROADCAST = automatic, every eligible online rider's phone rings at once, first to accept wins.

A SELF shop can now be BROADCAST — its own fleet's phones ring automatically without the shop having to misrepresent itself as PLATFORM and share orders with the wider pool. Staff can always fall back to manually calling a rider regardless of dispatch mode.

02How the app works

No technical terms — this is the flow to walk a new person through, and it is also the exact end-to-end test that Phase 1 of the roadmap runs.

Getting started, once per rider

  1. Rider installs the app and enters their phone number.
  2. They get a 4-digit code and type it in. (In development the code is always 1234.)
  3. First time only: they fill in vehicle details — type and registration number.
  4. They land on the home screen.

A normal working shift

  1. Rider taps a toggle to go online — saying "I'm available for work."
  2. A customer orders food elsewhere. The restaurant accepts it and starts cooking.
  3. When the food is packed, restaurant staff mark the order Ready.
  4. Every available rider who covers that restaurant is notified at the same time — phones ring with the shop name, item count, and cash to collect.
  5. The first rider to tap Accept gets the job. Everyone else who taps a moment later sees "Already taken" — nobody can double-book an order.
  6. The winning rider sees the pickup address, drop address, and the customer's name and phone.
  7. Rider drives to the restaurant and taps Picked Up. The system generates a 4-digit delivery code and shows it to the customer, in their app.
  8. Rider taps Out for Delivery and drives to the customer.
  9. At the door: the customer reads out their 4-digit code, the rider types it in — proving the rider reached the right person.
  10. Rider enters the cash actually collected and taps complete. A short amount still completes (with a reason) — the rider is never blocked from finishing. The shortfall is flagged for office staff to reconcile later.
  11. Delivery done — the order shows as delivered in the customer's app automatically.

When things go wrong — office staff can reassign a delivery to a different rider, cancel it, or force-complete it (for example, if the customer's phone is dead and the code can't be read out).

The one thing to understand about step 8

The notification goes to everyone at once; whoever taps first wins. Deliberate and simple — the fastest rider wins, not necessarily the closest. Fine with a handful of riders per zone; becomes a real problem past roughly five, which the roadmap records as the trigger to revisit it. Do not redesign this without asking.

03What is already built

Nearly all of the core loop exists in code — the caveat is entirely about which parts have been proven to work; see §4.

Backend — complete and committed for the whole rider lifecycle

  • Rider signup that never rejects an existing phone number, so a customer can also become a rider
  • Rider profile, go-online/offline, vehicle registration
  • Delivery zones, rider types, and the rule deciding whose phone rings
  • Automatic dispatch when an order becomes Ready
  • Rider accept, with genuine protection against two riders taking the same order
  • Status progression, delivery-code generation, cash collection with shortfall flagging
  • Office-staff paths: reassign, cancel, force-complete, cash reconciliation
  • Order and delivery status kept in step automatically in both directions — including: cancelling an order terminates a live delivery
  • (6 Aug) dispatchMode (independent of delivery mode, ADR-0019) plus DELIVERY_ASSIGNED/DELIVERY_REVOKED rider push on staff assign/reassign/cancel — including the customer-cancels-the-order path, which previously terminated a delivery with no audit trail and no notification at all

Rider app — the full loop has screens

  • Phone + code login, signup, vehicle registration
  • Home screen with the online toggle and the rider's deliveries
  • Incoming-offer screen that rings, with Accept / Dismiss and "Already taken" handling
  • Active-delivery screen with status buttons and location sending
  • Delivery-code + cash completion

Web admin — built and committed

  • Manage riders and their type/shop
  • Create and edit delivery zones, add shops and riders to them
  • A panel showing shop staff which riders are online, so they can phone them directly

Customer app

  • Shows the 4-digit delivery code on the order screen — previously a hard blocker, now fixed
Quality note

The tricky concurrency parts were done carefully and deliberately — the double-booking protection and the accept endpoint both contain non-obvious choices that are correct on purpose. code_map.md records why for each, marked "don't 'fix' this." Read those notes before touching them.

04What is not built, and the honest status

The single most important fact

Steps 1–2 and 10–15 of the §2 journey are device-verified (6 Aug) — steps 3–9, the actual broadcast/ring/accept loop, are not. A shop's staff manually assigning or cancelling a delivery correctly rings the rider's phone and syncs status. But nobody has watched an order reach Ready, watched every eligible rider's phone ring at once, and watched the first tap win — that specific loop has never run on a real device, at any point in this feature's history.

Do not treat "assign/cancel works" as evidence the broadcast loop works too — they share almost no code path. Phase 1 of the roadmap exists to establish that the broadcast loop actually works.

Risks that are worse than missing features

These look like they work but fail silently. They are the priority.

  1. A shop set to PLATFORM but not placed in any zone does nothing at all. Orders reach Ready, no phone ever rings, and the only trace is a line in a server log. The shop appears fully configured. This will happen during a demo.
  2. "All riders ignored it" is indistinguishable from "no riders online." Dismissing an offer writes nothing anywhere — if every rider ignores an order, it simply sits at Ready with nobody alerted.
  3. Riders carry unlimited platform cash. Cash is recorded and reconciled afterwards, but nothing stops one rider accumulating a large amount across many deliveries before depositing any of it. Every control is after-the-fact — a money-loss risk, not a technical one.
  4. The loud ring may quietly become a normal notification. An Android policy change (Jan 2025) restricts full-screen alerts to phone/messaging/alarm apps. A delivery app doesn't qualify, and the system downgrades silently rather than reporting an error.
  5. "Online" is an unverified self-declaration. No heartbeat, no idle location, no record of who accepts or ignores work. Staff can be shown a rider who's asleep.
  6. A zone has no geographic boundary. It groups shops, so it controls where a rider picks up — but nothing limits how far the drop-off can be.
Resolved — was previously a launch blocker

This section used to warn that Ninjasu_Rider_App was entirely untracked in git, one careless cleanup command from total loss. As of 6 Aug the repo has real history on main — no longer a single-commit risk. Not independently re-verified whether .env/secrets are correctly gitignored, so still worth a quick look before assuming that specific detail is clean.

05Decisions already locked

Treat these as settled. Each was decided deliberately — re-litigating them wastes time.

  • A delivery is never edited, only replaced. Reassigning keeps the old record as history and creates a new one. Never mutate a delivery in place.
  • The notification goes to everyone; first to accept wins. Not one-at-a-time offers, no queue, no ranking. Revisit only past ~5 riders per zone.
  • Nothing is written to the database until a rider accepts. There is no "offered" state.
  • Live location is fetched by polling, not a persistent connection (ADR-0013).
  • The delivery code proves the rider arrived — it does not prove the cash was right (ADR-0014). A short payment still completes and gets flagged; it must never trap the rider.
  • One on-duty device per rider (ADR-0015).
  • Riders are not shop staff. They are never invited through the shop team screen.
  • "Missions" is display text only. Never rename anything in the API, database, or code.

House rules that matter on day one

  • The backend is the only source of truth. Never re-implement a pricing, discount, or validation rule in the app — render what the API returns.
  • One HTTP client per app. Never write a second fetch wrapper.
  • Never put a font family in a stylesheet — use the shared text component.
  • Features must not import from each other; share through the store or shared folder.
  • Colours come from the constants file, never hard-coded.
